## KB Navigation Pattern (THE efficient way to find anything)

Follow this sequence, shortest path first. The goal is 5-8 calls max to understand any topic.

1. **Broad context**: `kb_context_pack("your topic here", limit=10)` -- ONE call returns symbols, docs, knowledge, data flow, blast radius, repo map, system overview. Start here for any unfamiliar topic.

2. **Find symbols**: `kb_search_symbols("function_name")` or `kb_search_symbols_semantic("what it does conceptually")` -- find exact functions, types, files with line numbers.

3. **File content**: `read_file(path, offset, limit)` -- read specific sections. Never read entire files. Use offset to jump to the line kb_search_symbols found.

4. **Impact analysis**: `kb_get_blast_radius("function")` -- what breaks if I change this. `kb_get_callers` / `kb_get_callees` for relationship tracing.

5. **Directory layout**: `kb_repo_map("vibepilot")` -- full tree with symbol annotations.

6. **Knowledge items**: `kb_search_knowledge("rules about prompts")` -- rules, architecture decisions, research reports.

**Never read raw files to "understand the system."** The KB already has everything indexed. 5-8 calls of the tools above replace 40 minutes of file browsing.

## What VibePilot Is

VibePilot is an **automated software factory**. You give it a PRD (markdown describing what to build) and it produces merged, tested, production-grade code with zero human involvement in the code itself.

It is a **quality control harness, not a todo app**. Every piece of output gets reviewed, tested, and validated before it lands. Models that produce bad output get penalized in routing. The goal is production-grade code, not "something that compiles."

### The Pipeline (one sentence per step)

1. PRD pushed → planner AI breaks it into tasks with target files and routing
2. Supervisor AI reviews the plan → approved or sent back for revision
3. Complex plans go to council (multiple models weigh in)
4. Each task dispatched to a task agent (free API via courier/browser-use, or direct API)
5. Task agent writes the code
6. Supervisor reviews every output against its prompt packet and expected output
7. Rejected work gets specific feedback, agent retries (up to 3 attempts)
8. Three testing layers: artifact validation, semgrep security, native tests
9. Passed tasks merge: task branch → module branch → testing branch → main
10. Merge conflicts go to maintenance agent (infrastructure problem, not task failure)
11. Done. PRD fully implemented, tested, merged.

### Core Principles

- **Dashboard is sacred** -- what the human sees at a glance. Additive only, never touch without explicit OK.
- **Zero human code involvement** -- human does visual UI review, API budget decisions, and final yes/no on council research. Nothing else.
- **Config-driven, not hardcoded** -- models, routing, agents, connectors all in config JSON. Go is plumbing.
- **Free tiers first** -- courier agents use free web AI tiers via browser-use. Paid APIs only when free fails or human approves.
- **Retry with feedback, not blind retry** -- supervisor gives specific failure reasons. Model routing learns from outcomes.
- **Merge failures are infrastructure** -- conflict resolution goes to maintenance agent. No penalty to task agent.
- **Go serves the design, not the other way around** -- Go code implements what the architecture says. It does not invent new processes.

### Engineering Principles (EVERY LINE OF CODE ANSWERS TO THESE)

Every piece of VibePilot code, config, and architecture must be:

- **Modular** -- Each component does one thing. Swap one piece without touching the rest. No god objects, no tangled dependencies. If changing DNS means touching the governor, something is wrong.

- **Agnostic** -- No loyalty to any provider, framework, or vendor. Models, DNS, hosting, databases -- all swappable. Gemini today, something better tomorrow. Cloudflare tunnels today, something else next year. The system survives the swap because it never married the tool.

- **Swappable** -- If a component cannot be replaced in under an hour, it is too tightly coupled. Models swap via config. DNS swaps via one conf file. Hosting swaps via DNS pointer. Providers swap via `~/.hermes/config.yaml`. The only thing that does not swap is the principle of swappability itself.

- **Configurable** -- Runtime behavior comes from config files and database, not source code. If you have to recompile to change a model, a route, or a timeout, that is a bug. If you have to edit Go to change a prompt, that is a bug.

- **Robust** -- No hardcoded values. No fragile assumptions. No stubs that return empty and pretend to work. No shortcuts. No "I'll do that later" (if you can't do it properly now, stop and say so). No fixes that cause breakages elsewhere -- whackamole hell of fixing fixes is the number one enemy. Every fix must be root cause, not symptom patching. Test the fix, verify it does not break what was working.

**The anti-pattern to end all anti-patterns:** Fixing a bug by introducing a workaround that breaks something else, then fixing that breakage with another workaround, repeat until nobody understands the system. This is how projects die. When you catch yourself patching a patch, STOP. Find the root cause. Fix it once, properly.

### What the Human Does (3 things)

1. Visual UI/UX review (after the visual tester agent has checked)
2. Decides whether to add API credits when free tiers are exhausted
3. Final yes/no on council-reviewed research suggestions

That's it. The human does not code, merge, debug, review code, or fix conflicts. Ever.

## Absolute Rules

1. **NEVER hardcode anything.** Models, connectors, routing, agents -- all in config JSON files under `config/`.

2. **NEVER hunt for .env files in the vibepilot repo.** Governor credentials live in PostgreSQL vault (`secrets_vault` table, AES-256-GCM). Use `./governor vault list/get/set`. Hermes has its own `.env` at `~/.hermes/.env` for gateway config (API keys, model overrides) -- that's fine, don't touch it for governor credentials.

3. **KNOW EXACTLY WHAT YOU HAVE AND HOW IT WORKS BEFORE DOING ANYTHING.** This is not a suggestion. Read the knowledgebase. Check the session handover. Read the infrastructure reference. Query PostgreSQL. Read the existing code. Then and only then act. Agents that rush in to fix something they don't understand cause more damage than the original problem. Your first 5 minutes on any task is homework, not coding.

4. **DO YOUR HOMEWORK -- USE THE KNOWLEDGEBASE.** The knowledgebase exists because agents keep re-discovering what was already discovered. Before asking a question, before writing a line of code, before proposing a fix: check the knowledgebase (`http://localhost:8888`), check the session handover (`knowledgebase/research/session-YYYY-MM-DD-handoff.md`), check the infra reference, check `.hermes.md`. The answer is probably already there. Wasting an hour re-learning what took 5 minutes to document is a failure of discipline, not a lack of information.

5. **DASHBOARD LIVES AT VERCEL. Vercel auto-builds from every commit to VibesTribe/vibeflow main branch. The dashboard URL is https://vibeflow-dashboard.vercel.app/. NEVER push dist/ -- Vercel builds from source. NEVER assume the dashboard is served locally -- it is not. Source is at `~/vibeflow/apps/dashboard/`. Push source changes to GitHub main, Vercel deploys automatically. That is the entire deploy pipeline. No other steps. No local builds. No dist/.

6. **Schema migrations have ONE path. Use it. No exceptions.**
   Local PostgreSQL is the database. Migrations applied directly via psql:
   - `ls ~/vibepilot/governor/supabase/migrations/` -- find the NEXT unused number
   - Write `NNN_name.sql` with DROP IF EXISTS for idempotency
   - Commit and push to GitHub main
   - `cd ~/vibepilot && git pull`
   - `psql -d vibepilot -f /path/to/migration.sql`
   - Verify: `psql -d vibepilot -c "\df function_name"` or `\dt table_name`
   - Do NOT try any other method. Do NOT reuse existing numbers.

7. **IF IT IS NOT ON GITHUB, IT DOES NOT EXIST.** Local-only work is lost work. `git push` is not optional, it is the final step of every task. "I have it locally but haven't pushed yet" means "I have nothing." Local config files MUST be backed up to a repo. If it only lives on this disk, it is one disk failure from gone -- we learned this the hard way.

8. **NEVER take shortcuts or "do it later."** If you can't do it properly now, stop and say so.

9. **Go SERVES VibePilot's design. It does NOT invent new processes.**
   Go is plumbing. PostgreSQL is the contract. Dashboard shows what state IS.
   Go conforms to both. Not the other way around.

10. **Governor is a systemd user service.** `systemctl --user` and `journalctl --user`. Not sudo.

11. **Roles are defined in config, not guessed.**
    - Supervisor: reviews plans, reviews output, approves/escalates
    - Council: reviews complex plans and architecture
    - Human (Vibes): visual UI/UX decisions, strategic architecture yes/no. NOT technical. Does NOT code/merge/debug.
    - Maintenance: ONLY agent with git write access
    - Merge system: fully automated, zero human involvement

## Sources of Truth (MEMORIZE THIS)

**Two sources of truth exist. Nothing else.**

1. **GitHub** (VibesTribe org) -- all code, config, docs, prompts. If it is not pushed to GitHub, it does not exist. Local-only work is lost work.
2. **PostgreSQL** (vibepilot database) -- all runtime state: tasks, models, runs, costs, vault credentials, kanban. If it is not in PostgreSQL, it did not happen.

Everything else is a derived view or a temporary cache:
- The dashboard reads from PostgreSQL and GitHub. It does not own data.
- The knowledgebase Flask server is a view into PostgreSQL + a doc repo. It does not own data.
- `.context/` files are build artifacts. They rebuild from source. Do not treat them as truth.
- Local config files MUST be backed up to a repo. If it only lives on this disk, it is one disk failure from gone.

**Before making any decision, check the source of truth first.** Not the dashboard, not a doc, not your memory from last session. GitHub for code/config. PostgreSQL for state.

## Post-Task Discipline (MANDATORY AFTER EVERY ACCOMPLISHED GOAL)

**No task is complete until the record is updated.** This is how we maintain thread across sessions, crashes, disk failures, and agent switches. Every accomplished goal MUST be followed by these updates before moving on:

1. **Kanban** -- POST to `http://localhost:8888/api/todos`. Add completed item as `done`. Add any new items discovered during the work as `backlog`. Do this in real-time as work progresses, not batched at the end.

2. **Session handover** -- Update `knowledgebase/research/session-YYYY-MM-DD-handoff.md` with what was done, what changed, what's still open. This file is the lifeline for the next agent that lands here. Keep it current.

3. **Infrastructure reference** -- If you changed a service, port, config path, or architectural decision, update `knowledgebase/knowledge/operational/x220-infrastructure-reference.md` immediately.

4. **This file (.hermes.md)** -- If a new rule was learned the hard way, add it to Absolute Rules. If providers changed, update the providers section. If current state shifted, update Current State.

5. **Git commit and push** -- All changes to docs, code, and config must be committed and pushed to GitHub. Local-only work gets lost. `git push` is not optional.

6. **Summarize what you did** -- Tell the human what was accomplished, what files changed, and what the next step is. No silent completions.

**Why this exists:** We lost a full session's context when the SSHD died. We lost track of what was done and why. This discipline ensures that any agent, any session, can pick up exactly where the last one left off by reading the kanban, the handover doc, and this file. Five minutes of updating saves hours of re-discovery.

## Task Failure Diagnostic Loop (Analyst Agent)

**Status: FULLY WIRED AND TESTED.** E2E proof April 29.

When a task hits `diagnostic_trigger_attempts` ceiling (default 2 in system.json):

1. **Trigger**: `attempts >= config.execution.diagnostic_trigger_attempts` (default 2)
2. **Diagnosis**: Analyst agent (`analyst.md` prompt, 69 lines) reads ALL accumulated failure feedback
3. **Routing**: `routeAnalystDecision()` — re-prompt, split, exclude model, or surface to human
4. **Token tracking**: `record_internal_run` with role="analyst"
5. **Transformation**: Task never dies. It transforms: split, re-prompt, model exclusion, or surface.

**Files**: handlers_task.go (`runAnalystDiagnosis`, `ParseAnalystDecision`, `routeAnalystDecision`), config/prompts/analyst.md
