## KB Navigation Pattern (THE efficient way to find anything)

Follow this sequence, shortest path first. The goal is 5-8 calls max to understand any topic.

1. **Broad context**: `kb_context_pack("your topic here", limit=10)` -- ONE call returns symbols, docs, knowledge, data flow, blast radius, repo map, system overview. Start here for any unfamiliar topic.

2. **Find symbols**: `kb_search_symbols("function_name")` or `kb_search_symbols_semantic("what it does conceptually")` -- find exact functions, types, files with line numbers.

3. **File content**: `read_file(path, offset, limit)` -- read specific sections. Never read entire files. Use offset to jump to the line kb_search_symbols found.

4. **Impact analysis**: `kb_get_blast_radius("function")` -- what breaks if I change this. `kb_get_callers` / `kb_get_callees` for relationship tracing.

5. **Directory layout**: `kb_repo_map("vibepilot")` -- full tree with symbol annotations.

6. **Knowledge items**: `kb_search_knowledge("rules about prompts")` -- rules, architecture decisions, research reports.

**Never read raw files to "understand the system."** The KB already has everything indexed. 5-8 calls of the tools above replace 40 minutes of file browsing.

## What VibePilot Is

VibePilot is an **automated software factory**. You give it a PRD (markdown describing what to build) and it produces merged, tested, production-grade code with zero human involvement in the code itself.

It is a **quality control harness, not a todo app**. Every piece of output gets reviewed, tested, and validated before it lands. Models that produce bad output get penalized in routing. The goal is production-grade code, not "something that compiles."

### The Pipeline (one sentence per step)

1. PRD pushed → planner AI breaks it into tasks with target files and routing
2. Supervisor AI reviews the plan → approved or sent back for revision
3. Complex plans go to council (multiple models weigh in)
4. Each task dispatched to a task agent (free API via courier/browser-use, or direct API)
5. Task agent writes the code
6. Supervisor reviews every output against its prompt packet and expected output
7. Rejected work gets specific feedback, agent retries (up to 3 attempts)
8. Three testing layers: artifact validation, semgrep security, native tests
9. Passed tasks merge: task branch → module branch → testing branch → main
10. Merge conflicts go to maintenance agent (infrastructure problem, not task failure)
11. Done. PRD fully implemented, tested, merged.

### Core Principles

- **Dashboard is sacred** -- what the human sees at a glance. Additive only, never touch without explicit OK.
- **Zero human code involvement** -- human does visual UI review, API budget decisions, and final yes/no on council research. Nothing else.
- **Config-driven, not hardcoded** -- models, routing, agents, connectors all in config JSON. Go is plumbing.
- **Free tiers first** -- courier agents use free web AI tiers via browser-use. Paid APIs only when free fails or human approves.
- **Retry with feedback, not blind retry** -- supervisor gives specific failure reasons. Model routing learns from outcomes.
- **Merge failures are infrastructure** -- conflict resolution goes to maintenance agent. No penalty to task agent.
- **Go serves the design, not the other way around** -- Go code implements what the architecture says. It does not invent new processes.

### What the Human Does (3 things)

1. Visual UI/UX review (after the visual tester agent has checked)
2. Decides whether to add API credits when free tiers are exhausted
3. Final yes/no on council-reviewed research suggestions

That's it. The human does not code, merge, debug, review code, or fix conflicts. Ever.

## Absolute Rules

1. **NEVER hardcode anything.** Models, connectors, routing, agents -- all in config JSON files under `config/`.

2. **NEVER hunt for .env files.** Credentials live in PostgreSQL vault (`secrets_vault` table, AES-256-GCM). Period. No .env files exist. Use `./governor vault list/get/set`.

3. **NEVER guess, estimate, or assume -- check first.** Query knowledge.db, read existing code, check what's there before inventing anything. Guessing token counts, timing, or any numeric value without checking is the same as guessing anything else.

4. **Schema migrations have ONE path. Use it. No exceptions.**
   Local PostgreSQL is the database. Migrations applied directly via psql:
   - `ls ~/VibePilot/docs/supabase-schema/` -- find the NEXT unused number
   - Write `NNN_name.sql` with DROP IF EXISTS for idempotency
   - Commit and push to GitHub main
   - `cd ~/vibepilot && git pull`
   - `psql -d vibepilot -f /path/to/migration.sql`
   - Verify: `psql -d vibepilot -c "\df function_name"` or `\dt table_name`
   - Do NOT try any other method. Do NOT reuse existing numbers.

5. **ALWAYS push to GitHub.** Local-only work gets lost.
   Local config files MUST be backed up to `backup/` in the repo.
   If it only exists on this machine, it doesn't exist.

6. **NEVER take shortcuts or "do it later."** If you can't do it properly now, stop and say so.

7. **Go SERVES VibePilot's design. It does NOT invent new processes.**
   Go is plumbing. PostgreSQL is the contract. Dashboard shows what state IS.
   Go conforms to both. Not the other way around.

8. **Governor is a systemd user service.** `systemctl --user` and `journalctl --user`. Not sudo.

9. **Roles are defined in config, not guessed.**
   - Supervisor: reviews plans, reviews output, approves/escalates
   - Council: reviews complex plans and architecture
   - Human (Vibes): visual UI/UX decisions, strategic architecture yes/no. NOT technical. Does NOT code/merge/debug.
   - Maintenance: ONLY agent with git write access
   - Merge system: fully automated, zero human involvement

10. **Read before you code.** Query knowledge.db first. 5 minutes of reading saves hours of rewriting.

## Task Lifecycle & Git Architecture

**READ VIBEPILOT_WHAT_YOU_NEED_TO_KNOW.md Section 6 for the canonical pipeline.**

The pipeline has 11 stages. The critical distinctions:
- **Supervisor** reviews: plan quality (step 3) + output alignment (step 6)
- **Council** reviews: complex plan architecture (step 3 only, supervisor triggers)
- **Testing handler** validates: code correctness (step 7) -- three layers: output validation, semgrep, native tests
- **Module branches**: task branch → module branch (after individual test) → project main (after module integration test)
- **Testing is NEVER skipped.** It is fixed to be project-aware, not skipped.

## Task Failure Diagnostic Loop (Analyst Agent)

**Status: FULLY WIRED AND TESTED.** E2E proof April 29.

When a task hits `diagnostic_trigger_attempts` ceiling (default 2 in system.json):

1. **Trigger**: `attempts >= config.execution.diagnostic_trigger_attempts` (default 2)
2. **Diagnosis**: Analyst agent (`analyst.md` prompt, 69 lines) reads ALL accumulated failure feedback
3. **Routing**: `routeAnalystDecision()` — re-prompt, split, exclude model, or surface to human
4. **Token tracking**: `record_internal_run` with role="analyst"
5. **Transformation**: Task never dies. It transforms: split, re-prompt, model exclusion, or surface.

**Files**: handlers_task.go (`runAnalystDiagnosis`, `ParseAnalystDecision`, `routeAnalystDecision`), config/prompts/analyst.md
